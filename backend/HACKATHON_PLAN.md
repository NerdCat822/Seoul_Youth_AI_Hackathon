# 트라이로그 해커톤 작업 순서와 제출 계획

제출일은 **2026년 11월 21일(토), 한국 시간**이다. 시연 목표는 가게 사장님이 아이디어를 고르고, 시도를 저장하고, 주문 자료에서 전후 차이를 확인한 뒤 다음 시도를 남기는 것이다. 실제 접수 마감 시각은 전달받지 않았다. 아래 시간은 팀 작업을 위한 소요시간 추정이다.

### 데이터 계약과 예외 처리

1. 한 시도에는 제목, 분류, 시작일, 종료일, 메모가 있다. 서버의 서울 날짜 기준으로 시작 전·진행 중·확인 가능을 계산한다. 확인일은 종료일 다음 날이다. 성공한 결과가 있으면 완료 상태로 조회한다.
2. ERD 초안의 `DAILY_SALES`와 `DAILY_MENU_SALES`는 보고서가 필요로 하는 개념이다. 입력 파일은 SQL의 `pos_orders`처럼 주문 품목 한 줄이 한 행이다. `base_date`로 영업일을 정하고 `(영업일, 영수증 번호)`를 묶어 건수를 센다. 같은 영수증에 대상 메뉴가 두 줄 있어도 대상 주문은 한 건이다.
3. 단일 가게의 UTF-8 CSV 또는 단일 시트 XLSX를 받는다. 필수 열은 `base_date,receipt_id,store_id,menu2_cd,price,quantity,is_refunded`다. 날짜는 YYYY-MM-DD, 단가는 0 이상 정수, 수량은 1 이상 정수, 환불은 true/false다. 파일 한도는 5MB, 데이터는 50,000행이다. Excel의 날짜 셀과 값만 있는 표를 사용할 수 있다.
4. 시작일부터 최대 14일을 변경 후 구간으로 하고, 정확히 14일 앞에 같은 길이의 변경 전 구간을 놓는다. 짧은 시도도 요일 구성이 같다. 예를 들어 11/07~09 시도는 10/24~26과 비교한다. 긴 시도는 첫 14일만 집계한다.
5. 환불 품목을 빼고 전체·대상 영수증 수, `단가 × 수량` 합계, 대상 비중과 전후 차이(%p)를 계산한다. 워크시트 오류·대상 코드 오타·누락 영업일·전체 유효 주문 0건 등은 필요한 수정을 반환한다. 휴무일을 나타내는 별도 열이 없어 빠진 날짜는 자료 확인 대상으로 둔다.
6. 계산이 모두 성공했을 때만 결과를 시도에 연결한다. 새로고침은 같은 결과를 읽고, 재업로드 실패 시 직전 결과가 남는다. 업로드 원본은 보관하지 않는다. 서버를 재시작하면 시도와 보고서가 초기화된다.

### 제출용 실행

JDK 17 이상과 Gradle 8.14.7, Node.js 22.12 이상 및 npm을 준비한다. 최초 의존성 설치에는 인터넷 연결이 필요하다. Java 17로 컴파일한다.

**터미널 1**을 저장소 루트에서 연다. 평소에는 실제 서울 날짜를 사용한다. 11/21 상태로 리허설할 때만 실행 전에 PowerShell에서 `$env:TRYLOG_DEMO_DATE = '2026-11-21'`을 설정한다. 날짜를 고정한 터미널을 닫으면 해당 설정도 끝난다.

```powershell
cd backend
gradle clean build
gradle bootRun
```

로컬 Gradle이 없으면 위 두 줄의 `gradle`을 Windows에서는 `.\gradlew.bat`, macOS/Linux에서는 `sh gradlew`로 바꾼다. 빌드된 JAR만 실행할 때는 `java -jar build/libs/trylog-backend-0.0.1-SNAPSHOT.jar`를 사용한다. 서버 상태는 `http://127.0.0.1:8080/api/v1/health`의 `UP`으로 확인한다.

**터미널 2**를 저장소 루트에서 열고 실행한다.

```powershell
cd frontend
npm ci
npm run build
npm run dev
```

브라우저에서 `http://127.0.0.1:5173`을 연다. Vite가 `/api`를 8080으로 전달한다. 발표가 끝나면 각 터미널에서 Ctrl+C로 종료한다. 정적 빌드 검수는 프런트 개발 서버를 종료한 후 `npm run preview`로 4173에서 진행할 수 있다. 두 실행 방식 모두 백엔드를 함께 띄운다.

### 7일 전망의 학습·검증 근거

지니네김밥의 8/01~11/20 일매출 112개를 사용했다. LightGBM 회귀 모델의 입력은 요일과 7·14·21·28일 전 매출이다. 10/24~11/20의 4개 주를 차례로 검증할 때마다 그 주의 시작 전에 관측된 행만 학습했다. 마지막으로 11/20까지 학습해 11/21~27을 전망했다. 화면의 **예측 방법**을 바꾸면 같은 날짜의 모델별 예상 매출을 비교할 수 있다. [재학습 명령과 입력 자료](forecast-tools/README.md)

| 같은 28일에서 평가한 방법 | 일평균 절대오차(MAE) | 전체 매출 대비 절대오차(WAPE) |
| --- | ---: | ---: |
| LightGBM 4.6.0 | 80,843원 | 12.94% |
| 최근 4주 같은 요일 평균 | 92,770원 | 14.85% |
| 직전 주 같은 요일 매출 | 111,704원 | 17.88% |

11/21의 LightGBM 예상 매출은 **772,372원**이다. 과거 검증 오차의 80번째 백분위(114,047원)를 적용한 참고 범위는 **658,325~886,419원**이다. 같은 요일 평균은 740,025원을 예상한다. 이 오차는 제공된 한 가게의 고정 기간에서 측정했다.

11/07~20의 시도 사례에는 별도의 과거 비교를 표시한다. 시도 시작 전에 알 수 있었던 4주 동요일 실적으로 예상한 2주 총액은 **9,032,900원**, POS 실제는 **9,329,700원**, 차이는 **+296,800원**이다. 사용자 업로드 결과와 고정된 시연 가게의 전망에는 각각 출처를 표시한다.
